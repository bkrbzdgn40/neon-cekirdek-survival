# M5.28 · Gameplay Evidence & Review Readiness

## Why this exists

The repository has original brand illustrations and a real playable browser build, but no approved real gameplay screenshots. A professional-facing page should not replace missing proof with invented concept images.

Steamworks' [store-review guidelines](https://partner.steamgames.com/doc/store/review_process) explicitly distinguish real game screenshots from pre-rendered art, marketing copy and concepts. We are not claiming a Steam release. The standard is useful as a discipline for any independent game presentation.

This milestone creates **repeatable review material rendered by the real running game**, while being honest about what automation can and cannot establish.

## What is captured

A separate Playwright configuration (`playwright.capture.config.cjs`) runs six Chromium screenshot scenarios from `tests/press.capture.spec.cjs`:

| File | Contents | Status |
| --- | --- | --- |
| `01-combat.png` | Actual gameplay canvas, tactical enemy actors and cockpit HUD | **Scripted scenario**, not organic play footage |
| `02-reactor.png` | Actual armed volatile reactor with risk ring and status warning | **Scripted scenario** |
| `03-graviton.png` | Actual graviton slow field and surrounding enemies | **Scripted scenario** |
| `04-boss.png` | Actual boss actor and boss HUD | Boss **position staged** for framing |
| `05-upgrades.png` | Actual game-generated three upgrade cards | Draws from the game's real choices |
| `06-mobile.png` | Actual running game at 390×844 Chromium viewport | **Emulated** device size, not a physical phone |

The capture script uses the real `index.html` and its game code/Canvas. It positions enemies/devices using existing game constructors/functions, not Photoshop, mock gameplay markup or a generated animation. Engine animation and layouts are real. Because each screenshot is an intentional test scene, it MUST be described as a **scripted capture** until a reviewed human game-session screenshot is recorded.

A manifest includes source commit, timestamp, viewport, screenshot size, and the prominent flag `approved_for_publication: false`. The contact sheet reiterates the same. No player data is collected or uploaded.

## How to run

Using Node 22 and the same dependencies already used in browser CI:

```sh
npm install --no-save --no-package-lock @playwright/test@1.56.1
npx playwright install chromium
npx playwright test --config=playwright.capture.config.cjs
```

Results are generated in `press-capture/`:
- six unaltered screenshots
- `manifest.json` with capture provenance and approval flag
- `contact-sheet.html` for local visual review

The main [CI workflow](../.github/workflows/neon-smoke.yml) runs the script after the normal Chromium tests and attaches `neon-gameplay-evidence` as a **30-day review artifact**. The artifact is *not* a permanent public screenshot gallery. A failing capture fails the browser job so a broken scene cannot silently pass.

## Human publishing gate

1. Download `neon-gameplay-evidence` from a **successful main CI run**.
2. Open `contact-sheet.html` and inspect each image at native resolution: HUD clipping, empty frames, unintended overlays, readable boss identity and whether the image makes gameplay understandable.
3. Reject poor captures, confirm the source commit matches the intended build and capture at least one genuine non-scripted play-session screenshot/video manually.
4. If media is accepted, copy the **selected** files under a deliberate versioned public folder (e.g. `media/gameplay/`) in a **separate reviewed PR**, and update the showcase to use those real assets with accurate captions.
5. Only then use selected files in game listings or press contact materials. Check usage rights and any store-specific artwork rules.

No workflow auto-pushes binary media to main; no write token is required for public PR CI. Screenshots are **not** pixel-diff baselines and do not guarantee artistic quality. The site still loads the live game only on demand.

## Reviewer path

A reviewer can inspect the actual build in a few minutes:

1. Open `showcase.html` and see the signature systems and boundaries. Use the preview to confirm it loads the real game.
2. Click **PLAY** and choose a chassis; move/aim and use **Space** dash, **E** EMP Nova, **C** Prism Riposte and **Q** Bastion when available.
3. Inspect the level-up module cards and note their readable descriptions, tier progression and different upgrade routes.
4. Check boss telegraphs and tactical battlefield devices in later waves. Reaching all systems during a short run is not guaranteed; the capture scripts provide *inspection fixtures* without rewriting gameplay.
5. Open [CI status](../.github/workflows/neon-smoke.yml), the [real-device QA protocol](DEVICE_QA.md) and the [press fact sheet](PRESSKIT.md) to distinguish automated evidence from long-session observations.
